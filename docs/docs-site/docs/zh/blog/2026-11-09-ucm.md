# UCM 官网博客正式上线：让 KV Cache 持续复用

UCM 官网现已开启博客页面。

这是 UCM 博客的第一篇文章。之后，我们会在这里持续发布技术设计、部署实践、性能评测和一线经验，把 KV Cache 管理与复用这件事讲清楚：我们为什么这样设计、在真实负载里遇到了什么、哪些优化有效、哪些结论只在特定条件下成立。

在展开后续内容之前，先介绍 UCM 本身。

## UCM 是什么

Unified Cache Manager（UCM）是一套面向大模型推理的 KV Cache 管理与复用系统。

在大模型推理中，Prefill 阶段会为输入上下文生成 KV Cache。多轮对话、长上下文推理、Coding 和多 Agent 协作等场景有一个共同点：系统提示、工具定义、项目代码和对话历史会在连续请求中大量重复。如果每个请求都从头计算这些相同前缀，就会反复做同样的 Prefill。

进程内的 KV Cache 又受限于显存容量和进程生命周期。服务重启、扩缩容或切换到另一个实例后，之前计算过的内容往往无法继续使用。

UCM 的做法是把可复用的 KV Cache 持久化到外部存储，并在不同请求和兼容的推理实例之间共享：

- **跨请求复用**：相同前缀直接复用已有 KV Cache，不再重复 Prefill；
- **跨进程持久化**：服务重启、扩缩容后，缓存仍然可用；
- **跨实例共享**：兼容实例可以复用彼此已经计算过的 KV Cache。

外部存储把缓存容量从单机显存扩展为更大的共享池，让“算过一次”的结果可以持续被使用。

## 它带来什么

与 vLLM 集成后，UCM 在多轮对话、长上下文推理等重复前缀较多的场景下，可以实现 **3–10 倍的推理延迟降低**。

除了 Prefix Cache，UCM 也在围绕稀疏化、PD 分离（Prefill/Decode Disaggregation）等方向优化吞吐和推理成本。我们的目标不只是“多缓存一点”，而是让缓存成为推理基础设施的一部分：可持久化、可共享、可观测，也可以被容量规划。

## 从哪里开始

- 想先跑起来：从[快速开始](../user-guide/quick_start/index.md)选择安装制品、配置引擎，启动第一个接入 UCM 的服务；
- 想确认环境是否支持：查看[支持矩阵](../user-guide/support-matrix/index.md)，了解引擎、模型、设备和功能覆盖；
- 想理解内部机制：沿[开发者指南](../developer-guide/index.md)跟踪一条请求，理解缓存键、存储后端与指标；
- 想定位线上问题：阅读[运行与排障](../user-guide/observability/index.md)，判断缓存是否生效、后端是否健康；
- 想做容量规划：使用 [KV Cache 计算器](../toolkit/kv-cache-calculator.md)估算显存与存储需求。

UCM 提供 vLLM、vLLM-Ascend 和 SGLang 的集成路径。具体可安装的引擎与后端组合，以快速开始页面中的发布制品为准。
