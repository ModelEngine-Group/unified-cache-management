# testTool SOP：sglang KV 下发长稳场景模拟（长稳压测引导）

模拟真实推理引擎（sglang 类）把 KV cache 下发到存储的流量形态做长稳压测：批量多层块持续下发、多档块大小混合、千条请求规模、非零起点偏移、少量屏障后读回。input 采用不带 value 的格式（`testmode=1`，value 由系统生成）。

## 第一部分：场景建模（demo input 的语义）

`input/sglang_longrun_input.txt` 按 sglang KV offload 的真实下发形态建模（input 文件不支持注释，语义说明在本节）：

- **key 编码**：`req(3位) + layer(2位) + block(4位)` 九位十进制数字串（如 `001030001` = 请求 001、层 03、块 0001），对应 sglang 的 `(request_id, layer_idx, block_idx)` KV 定位语义；key 空间 10 请求 × 5 层 × 25 块 = 1250 组合，单圈 1100 条 put 不重复
- **块大小档位**：模拟不同模型结构的每层 KV 块量级——`4096`（MLA 压缩 KV 小块）/ `65536`（GQA 常规层块）/ `262144`（多 token 聚合块）/ `1048576`（长上下文聚合块）/ `4194304`（偶发大聚合），全部满足协议约束（offset/length 512 对齐、length 上限 0xFFFFFF）
- **请求规模与并发形态**：单圈 1159 条请求——50 个 put batch × 22 entry = 1100 条连续大并发（batch 间无 sleep，16 worker 游标领取满并发，模拟 sglang 持续批量下发），单圈注入约 620MB
- **offset 起点**：非全 0——多档 512 对齐偏移轮转（512B ~ 3MB 共 12 档，约七成 entry 非零起点），模拟块内偏移写入；约束 `offset + length ≤ 4194304`（值缓冲单块容量）
- **读写语义**：尾部 `sleep 1` 读写屏障 + 1 个 get batch 抽查 8 条（与 put 同 key/offset/length，均匀覆盖不同请求与块档位）——段末全员同步（barrier）保证 get 读到的必然是本圈刚写入的数据（读回内容由明细日志 value 字段人工核对）；demo 中 sleep 仅此一处屏障用途（正常请求不节律停顿），长稳时长控制靠 `runtime`、注入水位靠 `ratelimit_mb`
- **循环执行**：跑完一圈时间未到则从头再跑（圈循环机制既有，无需配置）；限时退出在圈末同步点判定（本 demo 一圈约 1~3 秒，检查点足够密）

## 第二部分：配置与启动

conf 副本（基于 `conf/test_config.conf` 复制）长稳模式五处调整——**buffersize 必须调**（demo 块内最大 offset+length 为 4MB，默认 1MB 会导致含大块的任务 build failed 被跳过）：

```ini
testmode = 1          # input 不带 value，系统生成（demo 即此格式）
runtime = 86400       # 24h 长稳（大秒值：86400=24h、604800=7d；runtime=0 为圈数模式）
ratelimit_mb = 0      # 注入限速上限（0 不限速；按目标水位填 MB/s）
buffersize = 4194304  # 值缓冲单块容量（字节）：须不小于 demo 单条最大 offset+length（4MB）；buffercount（默认 256）建议不小于 numjobs 与单 batch entry 数之积的量级，池不足时自带流控阻塞（不报错）
perf = on             # 压测模式仅记失败明细（缺省 off 全量明细，长稳数万圈会产生千万级明细行刷盘）
```

容器 FAKE 环境启动：

```bash
cd <仓库根>/kv_semantics/testTool
./build/testTool <conf 副本> conf/kv_client.conf input/sglang_longrun_input.txt
```

真机验证：kv client 副本换真机端点 conf（改法见 sop/0 第 4 节）；demo 的 `ns=sglang` 须与对端存储实际 namespace 一致——ns 名经哈希派生协议帧 namespace id，不一致会导致 put/get 全部 notfound。

## 第三部分：观察点与带宽统计口径

- **指标行**：过程看 `Scheduler metrics [1s]`（IOPS / traffic / TTFT / 错误率实时窗口），结束看 `Scheduler metrics total`（ops / traffic 汇总），完成标记 `======Test Completed Successfully=======`
- **notfound 读法**：get 段设计保证本圈先写后读——正常长稳应恒为 0；出现 notfound 优先核对 ns 是否一致、demo 是否被改动破坏了"先写后读 + sleep 段隔离"结构。读回内容正确性不做自动判定，由明细日志 value 字段人工核对
- **带宽统计口径**：metrics traffic 是 **IO 完成口径**——统计点在 kv client 请求返回之后、字节为成功 entry 的 length 总和，因此 `traffic/s` 是工具观察到的**应用层真实完成带宽**，不是注入计数
  - `ratelimit_mb`（注入控制：提交前按秒级窗口扣预算）与 `[1s]` traffic（完成度量）的对照恰好反映链路健康度：两者相等说明链路无积压；完成速率低于注入限速说明链路能力不足（如 FAKE 后端峰值约 575MB/s）
  - **线路级带宽**（含 KV 协议帧头、RDMA transport 开销、对齐填充）超出应用层工具可观测范围：testTool 只统计语义字节，线路真实占用需用系统级计数观察（网卡 `ethtool -S`、RDMA 统计、存储侧接收计数）
- **退出语义**：限时退出在圈末同步点判定，实际退出时刻最多比 runtime 晚一圈时长（本 demo 一圈约 1~3 秒），长稳误差可忽略

## 第四部分：常见问题

| 现象 | 处理 |
| --- | --- |
| get 全部 notfound | ns 与对端不一致（demo 用 `sglang`）；demo 首圈先写后读、不依赖历史数据，ns 正确时首圈即应命中 |
| 注入速率上不去 | demo 主体无节律 sleep，注入速率即链路能力（容器 FAKE 峰值约 575MB/s）；需压水位时配 `ratelimit_mb`，需提水位时增 worker / 增大块档位 |
| 想改块大小或 offset 分布 | 保持协议约束：key 为十进制数字串（低 64 位非全 0、不超 39 位）、offset/length 512 对齐、1 ≤ length ≤ 0xFFFFFF（最大可填 16776704）、offset + length ≤ buffersize |
| 想改块大小或 offset 分布 | 保持协议约束：key 为十进制数字串（低 64 位非全 0、不超 39 位）、offset/length 512 对齐、1 ≤ length ≤ 0xFFFFFF（最大可填 16776704）、offset + length ≤ buffersize |
| 想观察真实线路带宽 | 应用层 traffic 只是语义字节；线路占用看系统级计数（网卡 / RDMA / 存储侧），或对照 TTFT 与完成速率估算链路排队 |
