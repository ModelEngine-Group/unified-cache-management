# testTool 真机测试 SOP：构建引导与执行引导

适用场景：在一台新机器（目标环境）上构建 testTool 并**单独验证建链 + region 注册（regionRegister）链路**。
配套文件（`testTool/conf/`）：

| 文件 | 用途 |
| --- | --- |
| `conf/test_config.conf` | testTool 测试配置（缺省执行模式；只建链验证复制副本改 `onlyconnect=on`） |
| `conf/kv_client.conf` | kv client 配置（simu 缺省，RoCE / HCCP 模板段内置；真机验证复制副本改传输段与端点——单文件模式，建链端点即副本 `asu_info.N`） |

> region 并发使用安全性审查记录存放在文档工作区（D:/AI/testTool/region-concurrency-review.md），不在本目录。

---

## 第一部分：build 引导

### 1. 环境要求

- Linux（x86_64 或 ARM 均可，与工具可移植性约束一致）
- cmake >= 3.18，支持 C++17 的 g++（Ubuntu 24.04 的 build-essential 默认满足）
- git
- libibverbs-dev（RoCE provider 编入的构建依赖，CPU / NPU 链路均需要；缺失时一键脚本前置检测会报错提示安装）
- 网络：首次配置需在线拉取 fmt / spdlog（FetchContent）。目标机器无外网时，改用离线方式：`-DDOWNLOAD_DEPENDENCE=OFF` 并在 `testTool/` 下预置 `fmt/`、`spdlog/` 源码目录

### 2. 构建 kv client（必须先于 testTool）

testTool 链接 kv client 预构建库（头文件取 `kv_semantics/include`，库取 `kv_semantics/build-kv/src`），且 build-kv 是本机构建产物**不入 git**，新机器必须重新构建。

> 建链断链测试（CPU-over-RoCE / HCCP KV-over-RoCE 链路）：可直接用统一一键脚本 `bash scripts/build-kv-link.sh`（缺省 CPU 模式；NPU 链路加 `--mode npu`）完成本节与第 3 节的全部构建（前置依赖检测 + provider 开关均内置于脚本；CPU 模式编入 FAKE + RoCE 双 provider、NPU 模式编入 FAKE + RoCE + HCCP 三 provider，conf 改 `transport.provider_type` 即切换链路无需重编；要求当前分支含对应 provider 代码，不含时代码会给出明确报错）。

以下命令均在**仓库根**（unified-cache-management）执行：

```bash
# 方式一：simu 环境（FAKE 后端流程走通，无需真实设备；与一键脚本 CPU 模式等价——FAKE + RoCE 双 provider 编入；
#   HCCP 显式 OFF 与脚本一致——CMake 缓存变量"不传即沿用旧值"，本目录曾做过 ascend 构建时防 HCCP 残留）
cmake -S kv_semantics -B kv_semantics/build-kv -DRUNTIME_ENVIRONMENT=simu -DCMAKE_BUILD_TYPE=Release -DBUILD_KV_CLIENT_PROVIDER_ROCE=ON -DBUILD_KV_CLIENT_PROVIDER_FAKE=ON -DBUILD_KV_CLIENT_PROVIDER_HCCP_KV_OVER_ROCE=OFF

# 方式二：ascend 环境（真设备）——真机验证用
#   当前真机建链主用 HCCP KV-over-RoCE provider（推荐直接用一键脚本 --mode npu，见上方提示；
#   与脚本等价——FAKE + RoCE + HCCP 三 provider 编入）：
cmake -S kv_semantics -B kv_semantics/build-kv -DRUNTIME_ENVIRONMENT=ascend -DCMAKE_BUILD_TYPE=Release -DBUILD_KV_CLIENT_PROVIDER_HCCP_KV_OVER_ROCE=ON -DBUILD_KV_CLIENT_PROVIDER_ROCE=ON -DBUILD_KV_CLIENT_PROVIDER_FAKE=ON -DKV_CLIENT_CANN_ROOT=$ASCEND_HOME_PATH
#   AIV provider 需外部 libumc.a，按需开启；AICPU provider 改 -DBUILD_KV_CLIENT_PROVIDER_AICPU=ON

# 编译 kv client（只构建该目标，避免全量构建）
cmake --build kv_semantics/build-kv --target kv_client -j
```

说明：

- `RUNTIME_ENVIRONMENT` 仅接受 `simu` 或 `ascend`（非法值直接 FATAL_ERROR）
- `BUILD_KV_CLIENT_PROVIDER_FAKE` 默认 ON；AIV / AICPU / RoCE / HCCP 默认 OFF，真机传输按环境开启。上方两条手动命令与一键脚本一致（simu：FAKE + RoCE，HCCP 显式 OFF；ascend：FAKE + RoCE + HCCP），多 provider 共存产物改 conf 的 `transport.provider_type` 即可切换链路，无需重编。关闭项也显式写出：CMake 缓存变量"不传即沿用旧值"，共用 build-kv 目录在两种模式间切换时，显式开关防另一模式的 ON 残留引发矛盾报错
- 构建类型缺省 Release（产物随时可用于性能测试）；调试构建显式传 `-DCMAKE_BUILD_TYPE=Debug`
- 产物：`kv_semantics/build-kv/src/libkv_client.so`（及 libkv_transport.so）

### 3. 构建 testTool

```bash
# 仓库根执行：
cmake -S kv_semantics/testTool -B kv_semantics/testTool/build -DCMAKE_BUILD_TYPE=Release
cmake --build kv_semantics/testTool/build -j
# 产物：kv_semantics/testTool/build/testTool
```

或进入 `kv_semantics/testTool` 目录后 `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j`（与 README 一致；调试构建显式传 Debug）。

注意：曾在同一 `build` 目录做过 NPU 构建（`TESTTOOL_ENABLE_ASCEND=ON`，见 `sop/2`）的，重新走 CPU 构建时显式传 `-DTESTTOOL_ENABLE_ASCEND=OFF`——CMake 缓存变量"不传即沿用旧值"，残留 ON 会在无 CANN 环境的机器上配置报错。

编译选项与主工程一致（`-Wall -Werror`），任何告警都会导致构建失败，属预期行为。

## 第二部分：执行引导（真机验证建链 + regionRegister）

### 4. 修改 kv client 配置（唯一需要按环境改的地方）

复制 `conf/kv_client.conf` 为独立副本（如 `conf/kv_client_roce.conf`，不动仓库默认文件），改副本三处：

| 字段 | 说明 |
| --- | --- |
| `transport.provider_type` | `FAKE`（本地模拟，流程验证）→ 真机传输按链路改：`CPU`（CPU-over-RoCE）/ `HCCP_KV_OVER_ROCE`（NPU 数据面）/ `AIV` / `AICPU` |
| `transport.asu_ids` / `asu_info.N` | ASU 节点编号与端点——**单文件模式下建链端点的唯一来源**，改副本此两键即可（如需运行期刷新拓扑或对齐生产 M800 view service，见 `conf/kv_client.conf` 文末 view.config_path 说明恢复双文件模式） |
| `transport.device_id` | 按目标机器实际设备编号 |

RoCE / HCCP 传输旋钮模板段已内置 `conf/kv_client.conf`（各键含义与默认值见注释），副本中取消注释按环境改值即可。

testTool 侧复制 `conf/test_config.conf` 为副本改 `onlyconnect=on`（只建链验证，不解析 input）；可选调整：

- `buffercount` / `buffersize`：region 注册的块数与单块大小（当前 256 块 × 1MB = 256MB host 内存，按目标环境内存余量调整）
- `buffertype`：`cpu`（主机内存注册，MemoryType=HOST）/ `gpu`（CUDA 显存注册，MemoryType=DEVICE）/ `npu`（ACL NPU 内存注册，MemoryType=DEVICE）。注意：`gpu`/`npu` 须编入对应设备 SDK（`TESTTOOL_ENABLE_CUDA` / `TESTTOOL_ENABLE_ASCEND`），未编入时**启动直接报错退出**（不做主机内存模拟——模拟会产生"以为测通了实际没测通"的假阳性结果）
- `startcoreid` / `numjobs`：worker 绑核起始核与并发数（worker i 绑 startcoreid+i）。**绑核失败整测退出**（fail-fast，不裸跑降级）：`startcoreid + numjobs` 不得超过目标环境核数（`nproc` 查询），小核环境调小 startcoreid 或 numjobs

### 5. 启动命令（只建链验证）

```bash
cd <仓库根>/kv_semantics/testTool
KV_LOG_RATE_LIMIT_ENABLE=false ./build/testTool <test conf 副本(onlyconnect=on)> <kv client 副本>
```

- 只建链模式 **input 文件不传**（传入也会被忽略）
- 必须在 `testTool` 目录下启动：conf 等相对路径相对进程工作目录
- `KV_LOG_RATE_LIMIT_ENABLE=false`：关闭 kv 日志按调用点限流（缺省同一调用点 60s 窗口内最多 3 条、超出静默丢弃——多节点建链时 Init 日志会缺条）

### 6. 验证观察点（按日志时序）

进程起来后依次确认（testTool 全量日志落盘 `log/tt_*.log`；stdout 只有 kv client 库的建链日志与进程级 `[FAIL]` 错误输出）：

1. `======Test Starting=======` —— 启动标记（warn 级，任何 perf 配置下均可见）
2. kv client 建链日志（`AsuTransportImpl::Init ...` 系列）—— 真机端点连通性在此体现
3. `Scheduler: 256 value buffers registered (1048576 bytes each, type=host)` —— **regionRegister 成功的直接证据**（块数、单块字节数、注册内存类型）
4. `onlyconnect=on: connection established, waiting for Ctrl+C to exit...` —— 建链与注册全部完成，进程挂起等待
5. 需要结束时 `Ctrl+C`，日志出现 `onlyconnect=on: Ctrl+C received, exiting`，进程退出码 0

任一步缺失或进程提前退出：看 stdout 的 `[FAIL]` 行与 `log/tt_*.log`（warn/error 全部记录进主日志文件）；建链失败优先核查 kv client 副本 `asu_info.N` 端点与真实环境是否一致（单文件模式端点仅此一处，无双副本一致性问题）。

### 7. 进阶：全链路验证（建链 + IO）

建链验证通过后，可切换执行模式跑完整 IO（缺省 `conf/test_config.conf` 即执行模式 onlyconnect=off；此前为只建链改过副本的，改回 onlyconnect=off 或另复制一份）：

```bash
cd <仓库根>/kv_semantics/testTool
./build/testTool conf/test_config.conf <kv client 副本> input/input.txt
# input 参数可缺省，缺省取启动目录下 input.txt（相对当前工作目录查找，仓库样例在 input/ 子目录，
# 用缺省值需先把 input.txt 放到启动目录平铺位置）
# kv 日志缺省按调用点限流（同一调用点 60s 窗口内最多 3 条，超出静默丢弃）；排查日志缺条（如建链 Init 行数）时前置 KV_LOG_RATE_LIMIT_ENABLE=false
```

结束标记：`======Test Completed Successfully=======`；指标行含 `ops / traffic / tasks / notfound / mismatch`（notfound / mismatch 为观察指标，不算工具链失败；get/exist 任务汇总行在未命中数大于 0 时以 ERROR 级别输出，仅为醒目提示，判定仍看完成标记与明细核对）。

### 8. 常见问题

| 现象 | 处理 |
| --- | --- |
| 构建报 fmt/spdlog 拉取失败 | 检查网络；或 `-DDOWNLOAD_DEPENDENCE=OFF` + 预置源码目录 |
| 构建报 kv_client 库找不到 | kv client 未先构建，或构建目录不是 `kv_semantics/build-kv`（testTool 按此固定路径链接） |
| 建链失败（Init 报错） | 核对 kv client 副本 asu_info 端点与真实环境一致性、真实端点可达性 |
| 启动即报错 "buffertype=npu requires TESTTOOL_ENABLE_ASCEND"（gpu 同理 CUDA） | 预期 fail-fast：`gpu`/`npu` 未编入设备 SDK 不做主机内存模拟，直接报错退出防假阳性；按报错提示重编（NPU 用一键脚本 `bash scripts/build-kv-link.sh --mode npu`），或改副本 `buffertype=cpu` 测主机内存链路 |
| 进程起来后 stdout 无 testTool 日志 | 正常现象：testTool 日志只落盘 `log/tt_*.log`，stdout 仅 kv client 库日志与 `[FAIL]` 错误 |
| 配置加载失败 | 确认在 testTool 目录下启动（conf 等相对路径相对进程工作目录） |
| 进程结束时跳过静态析构直接终止（日志 flush 后 `_Exit`） | 预期兜底行为：kv client 库线程存在退出期不终止的既有缺陷（FAKE WorkerPool 无停止路径等），优雅收尾 `spdlog::shutdown` 会永久阻塞挂死；故 testTool 统一收尾改为 flush 落盘后 `_Exit` 强制退出（退出码语义不变）。库侧修复后可恢复优雅退出路径 |
